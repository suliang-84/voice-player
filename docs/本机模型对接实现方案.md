# 本机模型对接实现方案

假设 Qwen3-ASR-1.7B、ForcedAligner、FSMN-VAD、CAM++、SenseVoiceSmall 已经部署在**当前这台机器**上，本文给出后端服务（`voice-player-backend`）对接这些模型、完成转写及相关功能的实现方案。

> **状态：** 方案草稿，尚未开发。
> **未核实的内容：** 各模型的调用方式（接口、参数、单段长度上限）没有对照官方模型卡核实；内存占用和速度只是估算；PyTorch 对 Intel Mac 的支持情况是我的印象，没有实际验证。这几项都放在第二章的「可行性验证」里先做。

## 一、目标与范围

### 要完成的功能

| 功能 | 说明 |
|---|---|
| 句级时间戳转写 | 文字 + 每句的 start / end，替换现在的 faster-whisper |
| 说话人标注 | 声道内的匿名说话人（`spk0`、`spk1`） |
| 情感与声音事件 | 每句的情感标签，以及咳嗽、笑声、呼吸等事件 |
| 声纹 | 每个说话人的 192 维声纹，为跨通话识别打基础 |
| 串音过滤 | 去掉对方声音串进本声道产生的「幽灵文字」 |

### 与现有功能的关系

- 现有的大模型阶段（身份推断、场景分析、翻译，OpenAI 兼容接口）**保留不变**；只是其中的情绪分布和情感得分改由 SenseVoice 的结果汇总，不再让大模型猜。
- 现有的接口、数据库字段**只增不改**，前端不受影响。
- 现有的「跳过空音」是基于能量阈值的，本方案提供一个可选的升级路径：改用 VAD 结果（见 7.6）。

## 二、本机条件评估与可行性验证

### 2.1 本机条件

| 项 | 实际情况 | 影响 |
|---|---|---|
| CPU | Intel Core i5-1038NG7，4 核 | 没有 GPU 加速，推理会比较慢 |
| 内存 | 16GB | 几个模型同时常驻会很紧张 |
| GPU | 无独立 GPU，Intel Mac 没有 MPS | 只能用 CPU |
| Python | 3.13.5（后端虚拟环境） | 模型依赖是否兼容需要验证 |
| 已安装 | 后端环境里有 `faster-whisper 1.2.1`；没有 torch、funasr、modelscope | 模型运行环境需要单独准备 |

### 2.2 主要风险

1. **PyTorch 是否能装上。** 据我所知，PyTorch 官方在 2.2 之后不再提供 Intel Mac（x86_64）的安装包，而 Python 3.13 需要更新的 PyTorch。这意味着在当前后端环境里直接 `pip install torch` 很可能失败。这一点必须最先验证。
2. **速度。** 1.7B 参数的转写模型在 4 核 CPU 上，速度很可能慢于实时。21 分钟的双声道录音可能需要很久，必须先实测。
3. **内存。** 按全精度估算：Qwen3-ASR-1.7B 约 7GB，ForcedAligner 约 2–3GB，SenseVoiceSmall 约 1GB，再加运行时开销，合计超过 11GB，加上系统和后端本身，16GB 会进入内存交换。所以设计上不能让大模型同时常驻（见 4.3）。

### 2.3 第零步：可行性验证（先做，通过后再开发）

在**独立的环境**（推荐 Python 3.10 或 3.11，与后端环境分开）里逐项验证：

| 验证项 | 做法 | 通过标准 |
|---|---|---|
| 能否安装 | 在新虚拟环境安装 torch、funasr、Qwen3-ASR 所需的包 | 能 `import`，无编译错误 |
| 模型能否加载 | 分别加载 5 个模型，记录加载耗时和内存 | 全部加载成功，记下各自内存 |
| 速度 | 用 60 秒的真实录音（如 `audio_003` 的 `track_A.wav` 前 60 秒）跑完整流程，记录每个阶段耗时 | 算出每阶段的「处理耗时 / 音频时长」 |
| 峰值内存 | 完整流程期间观察进程内存峰值 | 低于 12GB，系统不出现严重交换 |
| 结果质量 | 人工对照这 60 秒的文字、时间戳 | 文字大体正确，时间戳误差在可接受范围 |

**验证后的决策：**

- 全部通过且速度可接受 → 按本文方案开发。
- 能跑但太慢 → 采用第八章的降级方案（保留 VAD、CAM++、SenseVoice 这些轻量模型，转写先用已安装的 faster-whisper）。
- 装不上 → 需要换环境（conda、Docker，或把模型放到另一台带 GPU 的机器，那时按《本地模型转写对接指南》执行）。

## 三、总体架构

模型放在**独立的本机 Worker 进程**里，主后端通过 `127.0.0.1` 调用它，不在后端进程内直接加载模型。

```
┌──────────────────────────────────┐            ┌───────────────────────────────────────┐
│ 主后端 voice-player-backend       │            │ 本机模型 Worker（独立进程、独立环境）    │
│ Python 3.13 / FastAPI            │  HTTP      │ 127.0.0.1:9000                         │
│                                  │ ─────────▶ │                                       │
│ Pipeline                         │ 提交任务    │ ModelManager（内存调度）                │
│  └ LocalWorkerProvider           │ 轮询进度    │  VAD → ASR → 对齐 → 说话人 → 情感       │
│     （实现 AsrProvider）          │ ◀───────── │ 任务队列 + 单个推理线程                 │
│ 串音过滤 → 落库 → 大模型分析/翻译  │  取结果     │                                       │
└──────────────────────────────────┘            └───────────────────────────────────────┘
        共享本机文件系统：Worker 直接读取主后端缓存里的声道 WAV
```

### 为什么用独立 Worker，而不是进程内加载

| 原因 | 说明 |
|---|---|
| 环境隔离 | 后端是 Python 3.13，模型依赖不一定兼容；独立环境可以选合适的 Python 版本 |
| 内存隔离 | 模型占用大量内存，放在 Web 进程里会拖累接口响应，模型崩溃也会带走整个后端 |
| 可独立重启 | 更换模型、调参数不用重启 API |
| 以后可搬迁 | 接口沿用《本地模型转写对接指南》的契约，将来把 Worker 搬到带 GPU 的机器，主后端只改一个地址 |

### 本机场景下对原契约的调整

1. **传路径，不传文件。** 主后端和 Worker 在同一台机器，`POST /v1/jobs` 直接传声道 WAV 的本地路径，省掉 40MB 的复制。Worker 只允许读取配置的白名单目录（`ASR_WORKER_ALLOWED_ROOTS`，默认主后端的 `data/cache`），并且只监听 `127.0.0.1`。
2. **一个任务包含 A、B 两路。** 这样 Worker 可以**按阶段、跨声道**处理（先把两路的 VAD 都做完，再两路的转写，依此类推），每个大模型只需加载一次（见 4.3）。

## 四、Worker 设计

### 4.1 目录结构

作为与后端同级的独立项目：

```
voice-player-asr-worker/
├── requirements.txt          # torch、funasr、Qwen3-ASR 相关依赖
├── worker/
│   ├── main.py               # FastAPI：/health、/v1/jobs 等
│   ├── config.py             # 模型目录、白名单目录、线程数、内存策略
│   ├── queue.py              # 任务队列 + 单个推理线程
│   ├── models.py             # ModelManager：按需加载 / 释放模型
│   └── stages/
│       ├── vad.py            # FSMN-VAD
│       ├── asr.py            # Qwen3-ASR
│       ├── align.py          # ForcedAligner
│       ├── speaker.py        # CAM++ 声纹 + 聚类
│       └── emotion.py        # SenseVoiceSmall
├── scripts/run.sh            # 启动脚本
└── tests/
```

### 4.2 接口

沿用《本地模型转写对接指南》第四章（`/health`、`/v1/jobs`、状态、结果、错误格式），差异只有创建任务：

```http
POST /v1/jobs
Content-Type: application/json

{
  "tracks": { "A": "/abs/path/track_A.wav", "B": "/abs/path/track_B.wav" },
  "language": null,
  "options": { "align": true, "speaker": true, "emotion": true, "includeEmbedding": false }
}
```

结果中每个片段多一个 `trackId` 字段，`speakers` 数组每项也带 `trackId`：

```json
{
  "schemaVersion": 1,
  "language": "en-US",
  "duration": 1272.64,
  "segments": [
    { "trackId": "A", "start": 0.52, "end": 3.10, "text": "Okay, let's get started.",
      "confidence": 0.91, "speaker": "spk0", "emotion": "neutral", "events": ["Speech"] }
  ],
  "speakers": [ { "trackId": "A", "label": "spk0", "embedding": [ "... 192 个浮点数" ] } ]
}
```

### 4.3 内存调度（ModelManager）

16GB 内存下的核心策略：**大模型同一时刻只驻留一个，按阶段切换。**

| 模型 | 体积 | 策略 |
|---|---|---|
| FSMN-VAD、CAM++ | 很小 | 常驻 |
| SenseVoiceSmall | 约 1GB | 按需加载，用完释放 |
| Qwen3-ASR-1.7B | 最大 | 按需加载，用完释放；与对齐模型不同时驻留 |
| ForcedAligner | 次大 | 按需加载，用完释放 |

**处理顺序是「阶段优先」而不是「声道优先」：**

```
VAD（A、B）→ 加载 ASR → 转写（A、B 的全部语音段）→ 释放 ASR
  → 加载对齐模型 → 对齐（A、B）→ 释放
  → CAM++（A、B）→ 加载 SenseVoice → 情感（A、B）→ 释放
```

这样每个大模型整个任务只加载一次。如果只按声道依次处理，A 声道处理完要把模型全部换出，再为 B 声道重新加载，大模型反复加载会很浪费时间。

配置 `ASR_WORKER_KEEP_RESIDENT=asr` 可以让某个模型常驻，用于验证后发现内存够用的情况。

### 4.4 各阶段细节

| 阶段 | 输入 | 输出 | 要点 |
|---|---|---|---|
| ① VAD | 声道 WAV | 语音段 `[(s, e)]` | 合并间隔小于 0.3 秒的相邻段；单段过长时按最长静音点切开，上限由 ASR 能处理的长度决定 |
| ② ASR | 每个语音段的音频 | 文本、语种 | 只转写语音段，静音部分不进模型；按批推理；语种取两路中说话时间更长的那个 |
| ③ 对齐 | 段音频 + 文本 | 字/词级时间 | 再按标点和超过约 0.8 秒的停顿合成句级 start / end；时间要加上该段起点偏移；对齐失败的句子回退到 VAD 段边界 |
| ④ 说话人 | 每个语音段 | 192 维向量 + 说话人标签 | 声道内凝聚聚类，相似度阈值决定人数；只有一类时标 `spk0`；每个说话人保存平均声纹 |
| ⑤ 情感 | 每个语音段 | 情感、事件、语种标签 | 解析模型输出的标签（如 `<\|HAPPY\|>`）为结构化字段，具体标签集以模型卡为准 |

**进度：** 按阶段加权上报，大致 VAD 5%、ASR 55%、对齐 20%、说话人 10%、情感 10%；ASR 阶段按「已转写语音时长 / 总语音时长」细分。

**失败降级：** 对齐、说话人、情感任一阶段失败，只丢掉对应字段，任务仍然完成；只有 VAD 或 ASR 失败才把任务标记为失败。

**取消：** `DELETE /v1/jobs/{id}` 设置取消标记，推理线程在每个批次之间检查，及时退出并释放模型。

### 5.1 `Pipeline` 的改动

现有 `_run` 对每个声道依次调用 `asr.transcribe(path, on_progress)`。为了支持「阶段优先」的跨声道处理，增加一个**可选**方法：

```python
# provider 有 transcribe_tracks 就用它，没有则退回原来的逐声道循环（faster-whisper 不受影响）
transcribe_tracks = getattr(self.asr, "transcribe_tracks", None)
if transcribe_tracks:
    language, segments, speakers = transcribe_tracks(
        {tid: self.storage.track_wav(audio_id, tid) for tid in tracks}, on_progress)
else:
    ...  # 现有逻辑
```

之后依次：串音过滤（见 7.4）→ 写入 `Transcript`（含新字段）→ 保存声纹 → 汇总情感写入 `Analysis` → 现有的大模型阶段。

### 5.2 数据库

**新增字段：**

| 表 | 字段 | 类型 |
|---|---|---|
| `transcripts` | `speaker_label` | `String(16)`，可空 |
| `transcripts` | `emotion` | `String(16)`，可空 |
| `transcripts` | `events` | `JSON`，可空 |

**新增表 `voiceprints`：** `audio_id`、`track_id`、`speaker_label` 三者为主键，`embedding` 存 192 个浮点数（`JSON` 或二进制）。

**迁移：** 当前代码用 `Base.metadata.create_all`，它**不会给已存在的表加列**。需要在 `Database.create_all` 里补一段轻量迁移：对每张表，用 `PRAGMA table_info` 检查缺失的列，缺的执行 `ALTER TABLE ... ADD COLUMN`。这只适用于 SQLite；如果以后换成其他数据库，再引入 Alembic。

## 六、数据流（完整）

```
上传音频 / 首次访问转写接口
  → Task 记录（processing）
  → Pipeline：拆出 A、B 声道 WAV（沿用 storage.track_wav）
  → LocalWorkerProvider.transcribe_tracks → Worker
        VAD → ASR → 对齐 → 说话人 → 情感（阶段优先）
  ← 片段 + 说话人声纹
  → 串音过滤
  → 写 Transcript（含 speaker / emotion / events）、voiceprints
  → 按说话人汇总情感 → 写 Analysis(speakers).emotionDistribution / sentimentScore
  → 大模型：身份、场景、翻译（失败不影响转写结果）
  → Task 完成，WebSocket 推送 transcription_completed
```

前端沿用现有的轮询和 WebSocket 机制，无需改动；聊天面板拿到新的可选字段后，后续可以展示说话人和情感。

## 七、各功能的实现要点

### 7.1 句级时间戳转写

VAD 切段 → ASR 转写 → 对齐出字词时间 → 按标点和停顿合成句。**时间基准始终是整条音频的开头**，每段的结果加上该段起点偏移。对齐失败时，该段用 VAD 的起止作为兜底，不丢句子。

### 7.2 说话人标注

每个声道各自聚类。双声道通话通常每路一个人，聚类结果一般只有一类，标 `spk0`；会议、转接等一路多人的场景才会出现 `spk1` 以后的标签。聚类阈值要用真实录音调。CAM++ 官方模型偏中文，英文录音（如 `audio_003`）的效果需要单独评估。

### 7.3 情感与事件

按段取标签，写入 `Transcript.emotion` 和 `Transcript.events`。**说话人的情绪分布和情感得分**按时长加权汇总：

- `emotionDistribution`：每种情感占该说话人总语音时长的比例，合计 1。
- `sentimentScore`：按下表映射后做时长加权平均，范围 -1 到 1。

| 情感 | 分值 |
|---|---|
| happy | +0.7 |
| surprised | +0.2 |
| neutral | 0 |
| sad | -0.5 |
| fearful | -0.5 |
| disgusted | -0.7 |
| angry | -0.8 |

汇总结果在 `_analyze` 里覆盖大模型返回的同名字段；SenseVoice 不可用时保持大模型的结果。

### 7.4 串音过滤

按声道转写时，对方的声音串进来会被转成「幽灵文字」。在两路合并之后处理：

1. 用已有的 `audio.frame_rms` 得到两路的逐帧音量。
2. 对每个片段，计算它在**本声道**和**另一声道**的平均音量。
3. 规则：另一声道比本声道响出 `CROSSTALK_MARGIN_DB`（默认 6dB）以上，**并且**该片段置信度低于 0.5 → 丢弃；另一声道响出 10dB 以上 → 直接丢弃。
4. 被丢弃的片段写日志，便于调参。

阈值要在 `audio_003` 这类串音明显的录音上调试，避免误删真正的轻声说话。

### 7.5 声纹

每个说话人保存平均声纹到 `voiceprints`。第一阶段**只存不用**；跨通话识别（余弦相似度匹配已登记的人）作为后续功能，需要先确认合规要求。**声纹属于生物特征数据**，存储和访问要按公司要求控制。

### 7.6 跳过空音升级（可选）

现在的联合静音靠能量阈值，容易被呼吸、底噪干扰。有了 VAD 结果以后，可以改成：**A、B 两路都没有语音段的时间**就是联合静音，不再依赖阈值调参。这是独立的后续优化，不影响本方案的主线。

## 八、性能与内存预案

先看第二章的验证结果，再选档位：

| 档位 | 条件 | 做法 |
|---|---|---|
| 完整档 | 速度、内存都可接受 | 按第四章全流程运行 |
| 精简档 | 能跑但转写太慢 | 转写改用已安装的 `faster-whisper`（CPU、int8 量化），保留 VAD、CAM++、SenseVoice 三个轻量模型；时间戳取 VAD 段边界，不做强制对齐 |
| 迁移档 | 本机装不上或跑不动 | 把 Worker 放到带 GPU 的机器，主后端改 `ASR_WORKER_URL`，其余不变 |

**无论哪档都适用的优化：**

- 只转写 VAD 切出的语音段，静音部分不进模型（会议录音里静音占相当比例）。
- 推理线程数设为物理核数（4），不要超线程。
- 同一时刻只运行一个任务，其余排队。
- **两段式输出（可选）：** 先产出「文字 + VAD 段时间」立即写库并标记完成，让用户尽早看到内容；对齐、说话人、情感作为第二阶段补充字段，完成后再写入。这需要给任务加一个「补充进度」，属于后续优化。

## 九、运维

- **启动：** `voice-player-asr-worker/scripts/run.sh` 激活独立虚拟环境，监听 `127.0.0.1:9000`。需要常驻时可以用 macOS 的 `launchd` 管理，崩溃自动重启。
- **健康检查：** 主后端在 `wait_ready` 里轮询 `/health`；Worker 没启动时，转写任务显示「转写引擎不可用」，Worker 启动后下次访问自动恢复。
- **模型目录：** 通过 `ASR_WORKER_MODEL_DIR` 指向本地目录，支持离线运行，不依赖联网下载。
- **日志：** Worker 记录各阶段耗时和内存峰值，便于后续调优；**不要在日志里输出转写文本和音频内容。**
- **端口安全：** 只绑定 `127.0.0.1`，不对外开放。

## 十二、风险与待确认

| 风险 | 应对 |
|---|---|
| PyTorch 在本机装不上 | 第零步先验证；备选 conda、Docker 或迁移到 GPU 机器 |
| CPU 速度太慢 | 精简档；只转写语音段；两段式输出 |
| 内存不足 | 阶段优先 + 大模型不同时驻留；必要时降低精度 |
| CAM++ 对英文效果差 | 先只用声道区分说话人，声道内聚类作为增强 |
| 模型调用方式与假设不符 | 第零步用真实模型验证，再回头调整 Worker 内部实现，对外契约不变 |
| 声纹合规 | 第一阶段只存不用；跨通话识别前先确认合规 |

**需要你确认：**

1. 这台机器上的模型现在是怎么装的（哪个 Python 版本、是否已经能跑）？这决定第零步能不能直接跳过。
2. 录音主要是中文还是英文？
3. 可接受的处理时长：一条 20 分钟的通话，转写需要在多久内完成？这决定选哪一档。
4. 声纹现在只存不用，是否可以？
5. 接受「两段式输出」吗（先出文字，后补说话人和情感）？
